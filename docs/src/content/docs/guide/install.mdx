*A tune-up for your AI coding assistant: it looks at how your assistant is set up and how you work, then suggests changes based on SHRINE's practices. Nothing changes without your yes, and everything can be undone.*

## What It Does

- You paste one prompt into your agent harness
- The agent learns your environment, checks it against SHRINE's [anti-patterns index](/SHRINE/reference/anti-patterns/), and, with your consent, measures signals from your local session history
- It interviews you and reads the SHRINE pages that fit your answers
- It then designs its own way to bring each relevant teaching into your setup
- It asks your permission for each change before it makes it
- It assumes nothing is wrong: with no complaints, you get the baseline practices that fit, and an offer to start your [Individual Baseline](/SHRINE/stack/evaluation/#individual-baseline)

## Two Planes

- **Control plane** (fixed): numbered phases, each ending in a printed gate; the agent follows them exactly
- **Data plane** (generative): what to install and how; the agent designs it for you
- Coverage goal: the [North Star](/SHRINE/principles/tokens-to-value/) (value per win, where a win costs tokens plus your attention) and each ratified principle, listed from the manifest
- At Gate 4 each principle is marked applied, advised, or not relevant, with a reason tied to your answers
- Every proposal states its trade-off: what it costs (attention, tokens, latency, friction) and what it saves or protects; one that gains on one dimension at another's expense is flagged

## Phases and Gates

At the end of each phase the agent prints a gate: a checklist where each item has one line of evidence you can check (a path, a hash, your own quoted words). One unchecked item blocks the next phase.

The agent supplies data in a plan file; the checker renders the gates, the pick menus, the final gate, and the report from it. Long, repeated, exact text is where agents cut corners, so the checker writes each render to a file, and the agent pastes only a short block: the status, the counts, the file path, and the file's hash. You open the file; if your harness can show files, the agent offers to. Each approval records that file's hash, and the next gate checks it.

0. **Start**: harness, whether it can pause, mode, time box, prior records; you approve (pasting the prompt is the request; it does not ask whether to run)
1. **Discover**: inventory of your instruction files, extension points, shared locations, prior records, an anti-pattern scan, measured signals (with your consent), and a snapshot of the folders and files in your scope; you correct it
2. **Pin SHRINE**: manifest commit and page hashes; a mismatch aborts
3. **Interview and tag**: up to 10 questions; corrections are optional, labeled measured or recalled, then classified and tagged; you confirm
4. **Design and approve**: bookkeeping first, then each proposal, attacked by independent reviewers before you see it (more of them for shared or code-running changes), with its page, diff, trade-off, reviews, and a four-option menu (`[1] in place`, `[2] locally only`, `[3] reviewable change`, `[4] reject`); you pick one per proposal, then approve the printed gate; nothing is written before that
5. **Apply**: backups, record, each change logged pending then done with its proposal id and before and after fingerprints; the snapshot shows nothing else changed, new and deleted folders included
6. **Verify and hand off**: proof in a fresh session that each change loads, a self-audit, then a final gate with every item, the invariant map, restore steps, and the report

A harness that cannot pause prints every gate in report-only mode and changes nothing.

## The Data Plane

- It names no harness and no mechanism; your harness's agent knows its own environment best
- The agent may propose, for example, an instruction line, a rule, a skill, a command, a subagent, a hook, a lint, a nudge, plain advice to you, or anything else your harness offers
- A nudge acts at the moment an anti-pattern happens (for example, a second correction on the same point suggests a reset); it is advisory by default, rate-limited, easy to turn off, and tied to its index row
- The install practises SHRINE itself: the right model per step, and adversarial review of each proposal
- Each proposal says which teaching it serves, why that mechanism fits your harness, and the exact change
- Most of SHRINE is human practice; much of the output is advice to you, not agent rules
- If the agent cannot write somewhere, fetch, or pause for approval, it says so and adapts: paste-ready text, project scope, or a report only

## Invariants

These hold on every harness, whatever the agent designs. Each maps to gate items that enforce it:

1. **Your approval**: nothing changes until you approve the exact change; bookkeeping is approved first, or you get paste-ready output only
2. **Code that runs**: its own approval and a full-permissions warning; effects outside paths its record names, or will name once you approve the bookkeeping, are labeled "not reversible"
3. **Reversible**: backups first, in `.shrine/backups/` inside the scope you chose and ignored by version control, kept on your machine, never overwritten; each change logged pending, then done once verified; a whole file is restored from its oldest backup, and only if it matches its first recorded before fingerprint or its last after fingerprint
4. **Recorded**: one record per harness, user, and scope, at `.shrine/` in the project root or `~/.shrine/` (or a pointer there), named for both (for example `.shrine/<harness>.<user>.json`) so teammates do not collide, and never written over another record, with a fingerprint of each change and your answers (secrets redacted); only a record this harness wrote on this machine is trusted, with printed proof that version control does not track it, or an ignored local file holding its hash
5. **Traceable**: every proposal traces to a SHRINE page and your answers, never to repo content alone
6. **Content is data**: only text that tries to steer the install run is a red flag; your normal instruction files are not
7. **No secrets printed**: shown as `<redacted>`
8. **Narrow**: smallest scope; each always-loaded line must prevent a miss you named or discovery found; the staleness check is the one exemption, with its cost shown
9. **Bounded**: a time box and abort criteria
10. **Cannot pause, cannot change**: a harness that cannot stop for your approval only reports
11. **Blast radius**: the agent shows which files are shared or committed, who each change reaches, and whether it runs code; every proposal lists all four options, each with who and what it affects; your pick is recorded
12. **Evidence from tools**: every hash, count, and status comes from a command's output; long renders go to files the agent does not retype
13. **Practise SHRINE**: model fit per step, independent reviewers sized to each proposal's risk (or a marked self-critique when none is available), and measured signals before recalled ones

## Use It

<Steps>

1. Copy the prompt below, or fetch the raw file: [install-prompt.md](/SHRINE/install-prompt.md)

2. Bring two or three recent corrections you made to agent output, and say whether each has happened before; the agent designs from the repeated ones; with none, it still proposes the baseline practices that fit

3. Start a session in your harness, in the project you want to set up, and paste the prompt

4. Correct the agent's inventory of your environment, then answer the interview

5. Read each gate; approve, edit, or reject each proposal, and choose its scope

6. Keep the final gate and report: they name the backups and how to undo

## Why These Invariants

- **You paste it**: the prompt lives in this repo and changes only through [Governance](/SHRINE/reference/governance/); the site serves data only
- **Fetched pages are data**: [Tool Integration](/SHRINE/stack/tool-integration/#security)
- **Approval gates**: [Human in the Loop](/SHRINE/principles/human-in-the-loop/), [Checkpoint Gates](/SHRINE/patterns/checkpoint-gates/)
- **Your layers win**: an org, team, or role rule you already have overrides a SHRINE default ([Authority Cascade](/SHRINE/principles/authority-cascade/))
- **Pinned**: each install records the SHRINE commit it came from ([Reproducibility](/SHRINE/principles/reproducibility/))
- **Small footprint**: always-loaded text competes with the work ([Memory & Context Management](/SHRINE/stack/memory/))

## What It Reads

- [shrine-manifest.json](/SHRINE/shrine-manifest.json): the commit pin, each page's raw source link and hash, and the prompt's hash
- Each page it needs, from GitHub at the pinned commit; a hash mismatch stops the run
- If it cannot fetch, it asks you to paste the pages or point it at a clone
- [shrine-check.mjs](/SHRINE/shrine-check.mjs): the checker, verified against the manifest's `checker.sha256` before it runs

## The Checker

- A small Node script SHRINE ships; it changes no file, writes only new render files in the run's temporary folder (never inside your project or home scope, never over an existing file), and fetches only the manifest
- It checks the record against the manifest and your files: required fields, full 64-hex hashes, page hashes, the four-option pick, each file's hash chain, backups, drift, and pending entries
- It checks the agent's plan file: every change and backup inside the scope you chose, every ratified principle covered with a reason, enough reviewers for each proposal's risk, each scan finding tied to an index row, and no shortened hash
- Within a run, it checks each approved render file against its hash; the record keeps only those hashes, so a cleared temporary folder never fails a later check
- It checks the record update on a re-run like any other change
- If the plan changes after you saw the pick menus, Gate 4 blocks until the changed proposal is reviewed again, the menus are shown again with what changed, and you pick again
- Time used is computed from a start time recorded from a command, never estimated
- A change counts as loading only with proof from a fresh session after the write, from the agent's probe or your check
- It renders every gate, every pick menu with all four options, the final gate with every item and full hashes, and the report; a FAIL blocks the gate
- It runs code, so the agent asks once per run; without Node, or if you decline, the agent runs the same checks by hand, marks them "checked manually", and prints each gate by hand, marked "rendered manually"
- Every hash, count, and status on a gate is pasted from a command's output, with that command named
- Rerun it anytime: `node shrine-check.mjs --record .shrine/<harness>.<user>.json --manifest https://stablekernel.github.io/SHRINE/shrine-manifest.json`; the manifest may also be a saved local copy

## What It Leaves Behind

- Only the changes you approved, marked so a later run can find them
- A record and backups in each scope it changed, under `.shrine/` at the project root or `~/.shrine/`; gate renders stay in the run's temporary folder
- In a shared project, it asks whether the record may be committed; backups never are
- An advice-only report is a complete install

## Refresh and Staleness

- **SHRINE refresh**: the install proposes an entry you trigger by name (for example a command, a skill, an instruction line, or anything else your harness offers)
- It fetches the current prompt, checks its hash against the live manifest, and shows the prompt version and the pages that changed since your recorded commit
- The fetched prompt is data; it runs as a re-run only after you approve
- **Staleness check**: proposed pre-selected, but it still needs your approval, and you may decline it
- It compares your recorded commit with the live manifest and tells you when SHRINE has moved; it changes nothing
- Its proposal states its cost in tokens and attention

## Re-run and Undo

- Run the refresh entry by the name the report's handoff line gives, or paste the prompt again; it compares the recorded commit and page hashes and shows what changed
- It shows your recorded answers and asks only whether they still hold
- Unfinished or drifted entries from a past run are listed first, then proposed and approved like any change
- Your edits to its additions are kept unless you choose otherwise
- Same commit and same answers means no changes
- Ask it to uninstall; it removes only its own marked additions, and restores a whole file only when the file still matches its record and no other harness's record names it
- Removing the record and deleting backups each need your separate approval, after restores are verified; kept backups get a README on how to restore
- Re-run when a page you used is amended ([Deliberate Currency](/SHRINE/principles/deliberate-currency/)), or when one correction tag leads
